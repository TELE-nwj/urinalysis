# 开始延迟与按键无响应检查报告

日期：2026-10-12。用户确认 third／scend sol 固件，未插 U 盘，开始检测延迟约3～4秒。

## 结论

最主要的问题是：存储的同步等待运行在 monitor 控制任务里。首次开始要先尝试新建 U 盘文件，再打开液滴采集并进入测量；运行中无盘重试也占用同一任务。按键驱动本身没有等待循环，但依赖该任务定期扫描，所以存储等待期间无法采到按键，短按及松手事件可能丢失。手机控制同样必须等待该任务执行。

本结论来自当前代码路径与原始 key.c 主机复现；没有打开串口或测量真实 CH376 响应时间。因此确定存在同步阻塞设计，但不能把实机3～4秒无条件归为驱动的“固定3秒超时”。

## 证据一：开始先等待 U 盘，再开始采集

`git/third/main/app/monitor/monitor.c:224–233` 的 APP_IDLE 开始分支依次执行：

```text
S1_storage_start()
S1_reset()
urine_capture_arm()
S1_enter()
set_state(APP_MEASURING)
```

`app/S1/S1.c:286–291`：S1_storage_start 无论是否有盘，都立即调用 storage_retry。

`app/S1/S1.c:261–275` → `service/storage/storage.c:185–188` → `media_sync():155–159`：未就绪就同步再次 storage_init。初始化重新设置主机模式并检查磁盘；无盘失败后才返回。没有“无 U 盘立即开始、存储另行处理”的快路径。

因此手机指令到达和被接受，不等于采集已经开始。存储返回之后才打开液滴中断、建立测量计时起点。APP 当前不会人为延迟3秒后发开始命令；SessionEngine.command 直接把指令送入待发队列。

## 证据二：无盘重试不断阻塞同一任务

`app/monitor/monitor.c:286–318`：monitor_step 顺序为 process_commands → input_poll → urine_poll → S1_run → tick_1s → ui_sync，之后再延时20ms。所谓“20ms循环”实际为“本轮工作耗时＋20ms”，不是固定20ms扫描任务。

`app/S1/S1.c:33,261–275,369`：测量中每轮检查是否需要恢复存储；失败后把下一次重试设为本次结束时刻＋5000ms。若一次尝试耗时3.5秒，则会出现约3.5秒的扫描空窗，恢复约5秒后又尝试；总周期约8.5秒。5秒是重试间隔，不是这次存储操作的超时。

存储区里的递归 SPI 互斥量并未把业务变成异步：拿锁、驱动通信、等待和释放都由 monitor 同步完成。这里也不是关闭所有硬件中断；液滴采集中断在测量中仍可运行，但控制、解算、显示和快照刷新会推迟。

## 证据三：轮询按键会漏掉短按，也会漏掉松手

`driver/key/key.c:32` 禁用 GPIO 中断；`key_scan():51–74` 每次读电平，连续3次一致才改变稳定态，稳定按下时直接同步调用回调。

`service/input/input.c` 只适配转发；`app/monitor/monitor.c:252–258` 的 on_key 同步调用 execute_command，所以按K1也会立即进入相同的存储等待。没有独立按键任务，也没有中断事件缓存。

两种直接后果：

1. 在等待窗口内按下又松开的键，扫描完全看不到，事件丢失，不是稍后补执行。
2. 若第一次按下已识别，但等待期间的松手没采到，第二次按下时驱动仍认为“键一直按着”，也不会再次触发；必须先采到连续3次释放才重新允许按下。

原始 key.c 主机模拟验证全部通过：正常20ms扫描识别两次按下；第一次K1回调阻塞3500ms期间的K2短按丢失；未采到K1释放时下一次K1按下丢失。测试位于 `.planning/control-latency-20261012/key-harness/`，使用已安装ESP GCC与RV32软件执行器、GPIO/时间替身，不模拟真实ESP调度、电气或CH376。未修改被测 key.c。

## 驱动超时与次要影响

- `driver/ch376/ch376_spi.c:142–173`：wait 循环上限500000，约500001次10µs忙等，明确延时部分约5秒，加上GPIO、循环与调度开销。其注释“约7秒”不是实测保证；芯片提前返回时可能只有3～4秒或更短。
- `ch376_spi.c:323` 的主机模式等待仅50ms，不能单独解释3～4秒。
- `sdkconfig:CONFIG_FREERTOS_HZ=100`：`pdMS_TO_TICKS(1)` 是0。wait 每256次调用的 vTaskDelay(0) 只让出执行机会，不是注释预期的“睡1ms”，降低CPU占用的设计没有正确实现。
- `service/mobile/mobile.c:289` 给命令5秒执行前截止；`monitor.c:274` 只在执行前判断。排队遇到长重试可能被判EXPIRED；一条已开始执行的start不会到5秒自动中断。APP在快照超过3秒未更新时判陈旧并禁用控制（SessionEngine.tick），会进一步表现为按钮不可操作。
- SPI/CH376/storage日志在 S1 存储区内被设为ESP_LOG_NONE（S1.c:96–97），所以现场不一定能看到 wait 内部等待日志，通常只见存储尝试结束后的失败提示。
- 屏幕发送/逐帧日志和ADC也在同任务，会增加扫描间隔；现有代码没有发现它们主动设置3～4秒等待。不应先把提高任务优先级或缩短按键消抖当根因修复。

## 修复建议（本次未实施）

1. 控制路径先完成开始/暂停/复位与采集状态改变；U盘新建、恢复、每分钟写盘由独立存储任务串行执行，状态机不等待介质。
2. 芯片初始化与介质状态分离：无盘不反复重新配置主机；缺盘探测有短且真实的单调时间截止，挂载/写入保留适当较长预算。
3. 按键独立扫描或采用中断＋消抖，只投递事件，回调不执行文件操作；保持唯一状态执行者，防止并发改状态。
4. 驱动让出CPU至少使用1个实际RTOS tick，超时按单调时钟而非迭代次数计算；这只是辅助，不能代替把阻塞移出控制任务。
5. 后续实机记录命令RX/accepted、存储开始/结束、状态转换、completed四组时间戳，分别验证未插盘与插盘、首次开始与暂停继续。目标是存储失败仍立即响应检测，实体短按不丢，手机快照不因探盘连续停更。
