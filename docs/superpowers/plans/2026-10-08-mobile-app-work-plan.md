# ESP32 尿量仪专用 Android App：工作计划（审核稿 V1）

> 面向执行智能体：用户审核通过后，使用 subagent-driven-development 执行小任务，使用 dispatching-parallel-agents 管理独立任务。当前只提交计划，没有启动开发或分派开发任务。

**目标：** 华为 nova 14 连接 ESP32 自建 Wi-Fi，使用专用 App 查看测量数据、电量和 U 盘状态，并发送一次时分秒及开始、暂停、复位命令。

**架构：** 沿用现有 main → app → service → driver → bsp。手机协议解析、校验和打包位于 service/mobile；monitor 是状态和计时的唯一执行者。App 与串口屏使用同一测量数据源。

**技术栈：** ESP32-S3、ESP-IDF v5.5.5、SoftAP、WebSocket/JSON；Android Kotlin、Jetpack Compose、ViewModel/StateFlow、OkHttp；Node.js 模拟设备；ESP-IDF Unity 与 Android 单元/UI 测试。

**审核状态：** 等待用户审核。本计划批准前不改固件、不创建 App 源码、不启动开发子智能体、不安装 SDK、不烧录。

## 1. 已确认需求与交付范围

- 目标手机只按 Android 路线开发，交付 APK，不开发 iOS 或第二套手机平台。
- 用户确认 nova 14 当前系统为安卓；以实际安装和网络访问验证作为兼容性证据，不再凭机型推断系统。
- ESP32 开热点，手机连接热点；不要求手机开热点，不依赖路由器或互联网。
- 单片机上报：累计尿量 mL、实时流速 mL/h、滴数、有效测量时间、测量状态、报警、电量、设备时钟和 U 盘状态。
- 手机在每次建立新的 App 通信会话后同步一次时分秒；单片机自行走时。确认成功后不周期对时。
- 手机支持开始/继续、暂停、复位；实体按键继续有效。
- 通信协议解析、校验、打包归中间业务层，不放 app/mobile 或硬件驱动。
- 第一版包含实时监测页和设备连接页。暂不增加云端、账号、历史曲线、历史导出、OTA、多手机控制或后台持续监护。
- CH376 驱动故障修复、PCB/引脚修改、计量阈值和电池标定不在本次开发范围。

## 5. 协议 V1 与控制规则

默认连接地址为 `ws://192.168.4.1/ws`。ESP32 使用 2.4GHz SoftAP，热点名 `NIAIO-xxxx`，首版只允许一个控制会话。密码通过统一配置入口设置，在集成前由主智能体与用户确定，不写入日志或交给 DeepSeek。

### 5.1 消息类型

| 类型 | 方向 | 必要内容 |
|---|---|---|
| hello | ESP32→App | v=1、device_id、boot_id、session_id |
| status | ESP32→App | seq、sample_uptime_ms、数据快照 |
| time_sync | App→ESP32 | session_id、req_id、hour/minute/second |
| command | App→ESP32 | session_id、req_id、action=start/pause/reset |
| ack | ESP32→App | req_id、phase、result、state、state_seq |

快照字段：`total_ml`、`rate_mlh`、`total_drops`、`elapsed_s`、`state`、`alert`、`battery_percent`、`storage_state`、`clock_hms`、`time_synced`。数值传输保留数值类型；电量未知使用 null；状态 IDLE/MEASURING/PAUSED；报警 A/B/C/D/E 在 App 映射为中文。

U 盘状态定义 UNKNOWN/ABSENT/READY/ERROR。只有已取得介质缺失证据才报 ABSENT，已确认可使用才报 READY。驱动未就绪或检查失败不能凭空推断物理状态。附带检查时间，手机知道状态是否陈旧。

### 5.2 一次对时

通信握手成功后发送 time_sync；时分秒严格限制为 0..23、0..59、0..59。ESP32 由 monitor 调 clock_sync_hms 并完成回执。App 确认后本会话不再发送；未获确认只使用同一 req_id 有限重试，最多3次，不建立无限周期对时。断线重建会话后重新同步一次。

### 5.3 状态机语义

| 当前状态 | start | pause | reset |
|---|---|---|---|
| IDLE | 开始新测量 | 无变化，回成功 | 清零并保持待开始 |
| MEASURING | 无变化，回成功 | 结算并暂停 | 清零并回待开始 |
| PAUSED | 继续原测量 | 无变化，回成功 | 清零并回待开始 |

实体 K1 保留切换语义，K2 保留复位语义，但执行都归统一命令处理入口。手机不发送 toggle。命令按到达执行队列的顺序处理，每条完成回执关联其 state_seq；App 不用晚到的回执覆盖更新的设备状态。

### 5.4 并发与异常规则

- 网络回调完成解析/校验后提交请求；不直接写测量数据、GPIO、时钟或存储。
- 入队成功只能回 accepted；monitor 实际处理后才回 completed。队列满返回 BUSY。
- 同会话同 req_id 同内容返回原结果，不重复执行；相同编号不同内容返回 INVALID_ARGUMENT。去重缓存上限32条。
- 首版控制队列容量8条，命令最大帧1024字节。过长、非法 JSON、未知版本/命令和无效数字必须明确拒绝。
- 请求进入队列时设置5秒有效期，执行前已过期返回 EXPIRED；执行中的存储操作不做不安全强制中断。
- App 5秒未获得完成结果显示“执行情况未确认”，不能假报成功或失败；断线重连不自动重放旧控制命令，先获取当前状态。
- 网络发送在网络上下文完成，不持有快照锁，不阻塞 monitor。快照锁只保护结构复制。
- 每秒推送完整状态；状态改变立即安排一次推送。App 看 sample_uptime_ms 判断数据是否更新，不能把重复发送旧快照当新数据。
- 3秒没有新快照显示数据陈旧；通信连接断开显示离线。两者不同：原有存储阻塞时网络仍可能在线。

## 6. 手机 UI 与交互验收

**实时监测页：** 顶部设备/连接状态、设备时钟；电量与U盘；突出累计尿量；并排流速和滴数；有效测量时间；三态与中文报警；主操作按钮；复位入口。

**设备页：** 设备名称、连接/重新连接、系统Wi-Fi设置入口、连接结果、对时结果和设备基本信息。首版优先允许用户通过系统设置连接热点，不承诺未经授权的静默 Wi-Fi 切换。

- 白色背景、深色读数、蓝色主操作。报警文字和颜色同时表达，不能只凭颜色判断。
- 控件按 dp/sp 适配，不按 nova 14 的物理像素硬编码；覆盖屏幕安全区、手势导航、大字体和竖屏。
- 主按钮显示开始/暂停/继续；等待处理显示正在执行。只有真实回执/快照才能更新为完成态。
- 复位确认清楚说明会清空本次尿量、滴数和计时，不删除U盘历史文件。
- 离线保留最后读数并标注更新时间，禁止控制按钮；未知电量显示 --，U盘未知显示未确认。
- 有效测量时间可超过24小时；墙上时钟按24小时回绕。暂停时有效计时冻结，墙钟继续。
- App进入后台或手机灭屏不向设备发送暂停/复位；回前台重建连接、重新取状态。首版不承诺后台持续接收或报警。

## 7. 多级智能体组织与真实并行限制

```text
L0 主智能体（本聊天）
├─ L1 固件负责人 F
│  ├─ L2 F1 控制/快照任务（负责人可亲自承担）
│  ├─ L2 F2 Wi-Fi/WebSocket 字节层
│  └─ L2 F3 中间层协议/手机服务
├─ L1 Android负责人 A
│  ├─ L2 A1 连接库/状态仓库（负责人可亲自承担）
│  └─ L2 A2 Compose 页面/交互
├─ L1 QA负责人 Q（开发组释放并发槽后启动）
│  ├─ L2 Q1 协议与状态机独立审查
│  └─ L2 Q2 App交互和设备测试
└─ DeepSeek/DSH 叶子任务 D1、D2、D3（由主智能体单一入口派发）
```

Codex 本会话最多4个活跃智能体，包含主智能体。首轮主+F+A占3个槽，第4个槽给一个有依赖满足的叶子任务；负责人可在自己的独占范围工作。不能同时再启动多个孙级智能体。叶子任务结束立即释放/复用槽，QA在开发负责人完成后开展独立审查。

DSH是外部模型通道，不冒充内置DeepSeek子智能体。当前只能确认GUI入口，不假设CLI/API已可用。主智能体通过已打开的DSH界面下达任务；GUI输入串行，DSH计算期间固件和Android组可以并行。任何子智能体不得抢占同一DSH窗口。

## 9. 主智能体的监督、评阅与接收

1. 下达前核验能力、目录、依赖与空闲槽。未批准的任务不启动，未冻结的合同不并行改。
2. 负责人在任务开始、接口完成、首次验证和完成时回报；发现阻碍立即回报。主智能体检查实际diff和进度，不只读“已完成”。
3. 使用代理状态/等待工具核对任务状态；保持监督窗口，阻塞等待不超过60秒，其他时间推进独立工作。DSH由主检查界面与实际产物，不频繁重复询问完整分析。
4. 父级先审需求符合性，再审实现质量；主智能体检查跨组接口、越界文件、测试证据和已知失败。开发者不能给自己的改动出最终验收结论。
5. QA记录问题等级和复现步骤，退回原所有者修复；原所有者无权删除失败测试或改低门槛。修复后重新审查受影响范围。
6. 只有主智能体标记 ACCEPTED；其他允许状态为 QUEUED/RUNNING/REVIEW/CHANGES_REQUESTED/BLOCKED。BLOCKED必须有具体外部条件。
7. 合并后运行完整集成检查。独立模块通过不代表整机通过；模拟器通过不代表nova14实机通过。
8. 对正在执行的工作定期给用户说明已确认事实、剩余风险和下一检查点，不报告虚构的百分比或 token 节省比例。

## 10. 测试命令与验收矩阵

工作树用实际绝对路径替换根目录，执行命令不得包含另一组目录的改写操作。

- 固件：在second sol目录、已激活ESP-IDF v5.5.5的终端运行 `idf.py -B build-mobile build`；预期生成本工作树固件，无编译/链接错误。
- 固件Unity：在tests/mobile-firmware独立测试工程运行 `idf.py -B build-tests build`；实际上板运行由主控制，记录PASS/FAIL用例数量。
- 模拟器：仓库根目录运行 `node tools/mobile/mock_device.mjs`；预期监听配置的本地地址，能切换正常、断线、延迟和乱序场景，不假冒真实硬件。
- Android：mobile-app目录运行 `./gradlew.bat :app:testDebugUnitTest :app:assembleDebug`；预期单测通过并生成APK。
- Android设备UI：用户授权并连接手机后，运行 `./gradlew.bat :app:connectedDebugAndroidTest`；预期交互场景通过，记录目标设备和系统API级别。

| 验收项目 | 可观察标准 |
|---|---|
| 安装与连接 | nova14实际安装启动，手动连ESP热点后建立App连接；无互联网仍可使用 |
| 数据一致 | 尿量/流速/滴数/计时/状态/报警与固件快照一致；串口屏同源；格式/单位一致 |
| 一次对时 | 同会话成功对时一次，随后10分钟抓包无周期对时；重连一次新会话再对时 |
| 三态控制 | 状态表9个组合逐项验证；重复start不会暂停，重复pause不会继续 |
| 去重 | 同req_id重发reset只执行一次；不同内容相同ID被拒绝 |
| 本地按键 | K1/K2与手机交替控制20次，状态、回执和页面不互相覆盖 |
| 时间 | 暂停冻结有效计时；墙钟继续；对时不改变累计测量时长；25h显示不回零 |
| 无效输入 | 非法JSON、越界时间、NaN/无效字段、超长帧、未知动作都得到明确错误 |
| 回执 | 队列满/过期/执行未确认都有正确UI；旧ACK不覆盖更新state_seq |
| 断线 | 10次断开/重连后无自动开始、暂停或复位；每次恢复当前实际状态 |
| 手机生命周期 | 后台/灭屏不改变设备状态；前台恢复后重新获取状态；权限拒绝可恢复 |
| 网络路由 | 蜂窝网络开启时仍能访问设备Wi-Fi；回原网络时App正确显示断开 |
| U盘状态 | 模拟四态全通过；实板依现有驱动实际结果报告，未实测不声称连接正常 |
| 存储阻塞 | 观测真实阻塞时长；数据陈旧/命令等待如实显示，不假成功、不多任务访问SPI |
| 稳定性 | 前台连接30分钟，资源无持续增长，关键事件回执完整，无异常重启 |

验收记录只允许 PASS/FAIL/NOT_RUN/BLOCKED，必须带命令输出、日志或截图及构建版本。CH376硬件问题可以不阻止手机通信阶段验收，但会阻止“真实U盘插拔状态全部通过”的结论。若当前存储阻塞导致控制体验无法接受，由主提出单独的存储异步化范围变更，不让子智能体擅自重构驱动。

## 11. 节约 token 与 DeepSeek 使用方法

- 给子智能体传简短、完整的任务包，不复制全会话、原理图、故障历史。
- 优先DeepSeek承担D1/D2/D3；它没有并发状态机、网络路由、协议语义、签名或最终评审权限。
- 相同合同只冻结一次；任务只回传变更摘要、实际验证与diff，完整证据落盘。
- 主与负责人按任务复用必要上下文；审查使用独立视角，避免开发者自证。
- DSH先做一个小任务试跑，验证能返回符合目录约束的产物；有问题缩小范围，不反复投递整个工程。
- DSH界面当前“完全权限”不等于得到本工程全部授权；先设置最小可用权限/隔离目录，做不到则仅接受纯文本输出。
- 不保证DeepSeek一定降低总token；如果返工明显超过简单任务收益，停止该类外包，报告事实并改由负责人处理。

## 12. 本次审核与批准后的顺序

用户审核的是功能范围、协议/对时语义、目录边界、UI、分工、权限和验收标准。批准后先执行P0/E0并回报首个可运行APK与本地网络证据，再展开并行开发。当前没有开发子智能体、没有DeepSeek任务、没有源代码修改或SDK安装。

配套工作流位于 `docs/superpowers/plans/2026-10-08-mobile-app-workflow.yaml`，负责人任务书位于同目录 `mobile-app-roles/`。YAML是依赖和审核门槛的定义；批准后使用真实多级子智能体执行，不用主智能体轮流扮演角色冒充并行开发。DeepSeek叶子任务经主智能体唯一DSH入口派发。

最终交付为一个Android APK、对应ESP32固件与源码、构建说明、协议V1、使用说明、验收报告和已知限制。正式签名、手机安装授权与实机烧录在产物具体可审查后处理；不会把开发签名APK描述成上架发布版本。
