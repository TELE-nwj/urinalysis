## 0. 测试环境（每次测试请先核对）

| 项 | 值 |
|---|---|
| 板卡 | ESP32-S3 |
| SDK | ESP-IDF v5.5.5 |
| 串口屏 | 淘晶驰 TJC / Nextion 类 |
| 通讯口 | UART1，115200 8N1 |
| 引脚 | MCU TX = `GPIO17` → 屏 RX；MCU RX = `GPIO18` ← 屏 TX（见 `main/bsp/pin_map.h`） |
| 日志口 | UART0（USB 串口，115200） |
| U 盘 | CH376 正常读写：登录时建 `<用户名>.TXT`，S3 测量中每分钟追加一行 |

### 控件对照（`main/service/screen/screen.c` 顶部宏）

| 宏 | 控件名 | 含义 |
|---|---|---|
| `CTRL_URINE` | `data.n0` | 累计尿量 ml |
| `CTRL_RATE` | `data.n1` | 速率 ml/h |
| `CTRL_DROPS` | `data.n2` | 累计滴数 |
| `CTRL_TIME` | `data.t1` | 计时/运行时间（文本） |
| `CTRL_STATUS` | `data.t0` | 状态/报警（文本） |

### 帧格式

- **MCU → 屏**：`控件.txt="值"` + `FF FF FF`
- **屏 → MCU**：`@用户名@命令\r\n`（用户名可含空格，不含 `@`）

## 1. T1 — 主函数直接读串口（接收链路）

- **日期**：2026-09-14
- **代码位置**：`main/main.c` → `app_main()` 主循环 ①
- **目的**：确认 MCU 能收到屏发来的数据，并确认**行尾字节**到底是 `\r\n` / `\n` / `\r`。

### 测试代码

```c
int n = screen_uart_read(rx, sizeof(rx), pdMS_TO_TICKS(50));
if (n > 0) {
    ESP_LOGI(TAG, "串口屏 RX %d 字节", n);
    ESP_LOG_BUFFER_HEXDUMP(TAG, rx, (uint16_t)n, ESP_LOG_INFO);   /* 原始字节 */

    for (int i = 0; i < n; i++) {                                  /* 文本形式 */
        uint8_t c = rx[i];
        txt[i] = (c >= 0x20 && c < 0x7F) ? (char)c : '.';
    }
    txt[n] = '\0';
    ESP_LOGI(TAG, "文本: %s", txt);
}
```

> ⚠️ 测试期间**不调用 `screen_init()`**：它内部 `screen_uart_set_rx_cb()` 会建一个
> `uart_rx` 任务把 UART 数据读走，主循环就读不到字节了。
> 改为只做显示初始化：`screen_set_page(0); screen_show_status("READY"); screen_show_urine(0.0f);`

### 预期现象

```
I (xxxx) main: 串口屏 RX 15 字节
I (xxxx) main: 40 45 ... 0d 0a
I (xxxx) main: 文本: @用户名@login..
```

- hex 行能直接看出行尾是 `0D 0A`
- 文本行的 `.` 表示不可见字符，`@用户名@命令` 一眼可读

### 结果

- [x] **合格**（用户确认）

## 2. T2 — 主函数每秒发送 5 个数据（发送链路）

- **日期**：2026-09-14
- **代码位置**：`main/main.c` → `app_main()` 主循环 ②
- **目的**：验证 MCU → 屏 的 5 个控件刷新是否正常（值变化 + 状态切换）。

### 测试代码

用**节拍计时**（`xTaskGetTickCount()`）保证 1 秒一轮，不受接收数据影响节奏：

```c
static const char *STATUS_TAB[] = {"READY", "MEASURE", "PAUSE", "LOGIN"};
uint32_t cnt = 0;                              /* 第几次发送(从 0 开始) */
TickType_t last_tx = xTaskGetTickCount();

for (;;) {
    /* ① 接收调试（同 T1） */
    ...

    /* ② 每 1 秒发一轮 5 个数据 */
    if (xTaskGetTickCount() - last_tx >= pdMS_TO_TICKS(1000)) {
        last_tx += pdMS_TO_TICKS(1000);

        float    v_urine = (float)(cnt + 1);   /* n0: 1,2,3,4 ... */
        float    v_rate  = (float)(cnt + 2);   /* n1: 2,3,4,5 ... */
        uint32_t drops   = cnt + 3;            /* n2: 3,4,5,6 ... */
        const char *status = STATUS_TAB[cnt % 4];

        snprintf(tbuf, sizeof(tbuf), "%lu", (unsigned long)(cnt + 4));  /* t1: 4,5,6,7 ... */

        screen_show_urine(v_urine);    /* data.n0.txt */
        screen_show_rate(v_rate);      /* data.n1.txt */
        screen_show_drops(drops);      /* data.n2.txt */
        screen_show_time(tbuf);        /* data.t1.txt */
        screen_show_status(status);    /* data.t0.txt */

        ESP_LOGI(TAG, "TX 第%lu轮: n0=%.0f n1=%.0f n2=%lu t1=%s t0=%s", ...);
        cnt++;
    }
}
```

### 预期现象（屏上应看到的节奏）

| 秒 | n0 | n1 | n2 | t1 | t0 |
|---|---|---|---|---|---|
| 1 | 1 | 2 | 3 | 4 | READY |
| 2 | 2 | 3 | 4 | 5 | MEASURE |
| 3 | 3 | 4 | 5 | 6 | PAUSE |
| 4 | 4 | 5 | 6 | 7 | LOGIN |
| 5 | 5 | 6 | 7 | 8 | READY |

串口日志同步输出：

```
I (1020) main: TX 第1轮: n0=1 n1=2 n2=3 t1=4 t0=READY
I (2020) main: TX 第2轮: n0=2 n1=3 n2=4 t1=5 t0=MEASURE
```

### 结果

- [x] **合格**（用户确认）——5 个控件每秒刷新正常，状态每秒切换正常。

## 3. T3 — 上电/复位后第一条命令被吞（**缺陷，已修复**）

- **日期**：2026-09-14
- **现象**：上电或复位后**第一次**发 `@用户名@login`，单片机不解析、无任何响应；
  日志只有驱动层的两行 RX dump，没有 `CMD=` 也没有状态切换：

```
I (519262) screen: RX 13 字节: @yfdf@login/n
I (519262) screen: 0x3fceb4c0  40 79 66 64 66 40 6c 6f  67 69 6e 2f 6e  |@yfdf@login/n|
（后面什么都没有）
```

- **根因**：屏在**上电/复位时会回传一帧 `1A FF FF FF`**。这三个字节既不是行尾
  （`\r`/`\n`）也不是 `/n`，所以**永远不会被切行**，一直赖在行缓冲里。
  等用户发第一帧命令时被追加到后面：

```
\x1A \xFF \xFF \xFF @ y f d f @ l o g i n / n
└── 残留启动帧 ──┘└──── 命令 ────┘
        → 交给 handle_cmd_line 的字符串首字符是 0x1A
        → if (line[0] != '@') return;  整帧丢弃，连日志都不打
```

  切完行缓冲被清零，所以之后的命令都正常 —— **只有"上电后第一条"被吃掉**。

- **修复**（`service/screen/screen.c`，两道防护）：
  1. `on_uart_rx()`：**行缓冲为空时只接受 `@`**，其它字节直接丢
     ```c
     if (s_rx_len == 0 && b != '@') continue;
     ```
  2. `handle_cmd_line()`：不再要求首字符是 `@`，**从行内第一个 `@` 开始解析**，
     并打 WARN 提示跳过了几个杂字节

- **结果**：✅ 已修（用户确认"上电后第一次登录就能成功"）

## 4. T4 — U盘文件"找不到 / 打不开"（**缺陷，已修复**）

- **日期**：2026-09-14
- **现象**：串口日志显示"创建文件成功、长度 48 字节、回读验证通过"，
  但把 U 盘插到电脑上**看不到文件 / 打不开，提示找不到文件**。
- **排查过程**：
  1. 把 `F:\ESP32\niaio\project`（参考工程，**已验证可跑**）的 `ch376_spi.c`
     与本工程逐行 diff → **底层 SPI/命令函数逐字节一致**，没有差异
  2. 定位到差异在**文件名大小写**
- **根因**：
  - 参考工程写的是 **`/ASD.TXT`（全大写 8.3）**
  - 我们写的是 **`/hoht.txt`（小写）**
  - CH376 的 `SET_FILE_NAME (0x2F)` 按手册**只支持 8.3 短文件名且字母必须大写**。
    传小写时芯片**能用同样字符串 `OPEN` 回来**（日志看着"成功"），
    但写进目录项的名字是坏的 → 电脑上找不到/打不开

- **修复**（`service/storage/storage.c` 的 `make_fname()`）：用户名统一转成 `/大写8.3.TXT`
  ```
  abc   → /ABC.TXT
  hoht  → /HOHT.TXT
  张三  → /__.TXT   ⚠️ 中文压成下划线，可能撞名
  ```
  同时**新增"落盘验证"**：建完文件后**重新挂载(0x31)再打开**（强制丢掉芯片内部缓存、
  重读磁盘），能读到长度才算真的落盘。

- **结果**：✅ 已修 —— 文件出现在 `H:\`，能正常打开（用户确认）

- **顺带修掉的另一个坑**：为了修"拔插 U 盘后旧文件复活"而加的 `media_sync()`
  里发了 `0x30 DISK_CONNECT` 但**没补 `0x31 MOUNT`**。
  `0x30` 会让芯片重新枚举 USB 设备、**作废已挂载的 FAT 上下文**，
  于是后续文件操作一律返回 `0x42 ERR_MISS_FILE`（文件未找到）——**哪怕文件就在盘上**。
  现已改成 **`0x30` 之后无条件补 `0x31`**。

## 5. T5 — 拔插 U 盘后已删除的文件"复活"（**缺陷，已修复**）

- **日期**：2026-09-14
- **现象**：在电脑上删掉的文件，把 U 盘插回板子后**又出现了**；
  同时板子新写的文件在电脑上找不到。
- **根因**：CH376 挂载后把 **FAT 表 + 根目录扇区缓存在芯片内部 RAM**。
  板子**只在开机时挂载一次**，之后不检测介质。
  U 盘在电脑上改过再插回，芯片仍拿**过期的目录缓存**读写 →
  旧目录扇区被写回（删除失效）、新目录项被覆盖（文件丢失）、FAT 两边交替写导致错乱。
- **修复**：`service/storage/media_sync()` —— 在 `login` / `start` 时
  （**必须没有文件打开**）做一次 `0x30 检测 + 0x31 重挂载`。
- **结果**：✅ 已修
- **另一处"删了又出现"的原因**：开机的 `TEST.TXT` 自检**每次上电都重建文件**，
  已删除该自检；另外 `login` 会重建不存在的 `<用户名>.TXT`，这是设计如此。

## 6. T6 — 速率 7 秒无新滴归零（**待确认**）

- **日期**：2026-09-14
- **需求**：串口屏显示的实时速率，如果 **7 秒没有新数据**就显示 0
- **实现**：`service/urine` 里用 `drop_last_time_us()`（硬件滴落时刻）判定
  ```c
  if (last != 0 && (now - last) > URINE_RATE_ZERO_MS * 1000ULL)
      m->rate_mlh = 0.0f;        /* URINE_RATE_ZERO_MS = 7000 */
  ```
- **预期**：滴几滴后停止，等 8~10 秒 → 屏上 `data.n1` 变 `0.0`；再滴一滴立刻恢复
